# ADR-028 — Select the standard-library exact-edge production router

Status: accepted for implementation, 13 October 2026. Supersedes ADR-019's
open production-router choice. ADR-027 still explains the reference
implementation's origin. This decision selects **one** production routing
implementation: the pure Python exact directed-edge Dijkstra algorithm in
`packages/simulation/routing/reference.py`, to be integrated with the OSM
compiler in Task 3.6. Valhalla is an evaluation-only development dependency;
it is not a second runtime router or fallback service.

## Decision basis

The routing contract requires run-specific hard closure of an exact directed
edge or every directed segment of an asset, stable edge-ID paths, integer
weights, conservative uncertain-turn handling, and boundary-cut accounting.
The standard-library implementation already expresses these operations. On the
reviewed synthetic fixture it passed 39 correctness tests, including both
bridge directions, car/emergency profile access, node-via and way-via `no` and
`only`, ambiguous/conditional exclusion, stable equal-cost ties, and cuts.
These tests establish algorithm behavior, not the future OSM compiler.

For the shared real-OSM probe, the pinned [Utrecht PBF](utrecht_netherlands.osm.pbf)
was inspected directly with [`osm_probe.py`](osm_probe.py). Its bridge way
`7010992` has `bridge=yes`, `layer=1`, `maxspeed=50`, two OSM nodes and no
`oneway` tag. Way `7010987` continues the same street. Relation `153969` is
`only_straight_on`, from way `310833905` through node `45150439` to way
`51978656`. The bounded [review graph](utrecht-bridge-graph.json) retains
those source IDs, tag values, coordinates, a source checksum, 328 nodes and
527 directed edges. It assumes a 30 km/h fallback and spherical segment
lengths, and intentionally does not compile all OSM access and turn rules.
Its seven case outcomes are compared with Valhalla's full Utrecht tiles in
[`bridge-reference-benchmark.json`](bridge-reference-benchmark.json) and
[`bridge-valhalla-benchmark.json`](bridge-valhalla-benchmark.json). Each route
was repeated 25 times, with input hash, path IDs, latency and process memory
recorded. The five common cases are forward/reverse bridge open/closed and the
node-via `only` turn. Both implementations take the bridge when open and
avoid it when closed, in both directions. Both follow the required straight
turn; the unrestricted reference counterfactual would turn directly in
20.903 m / 3 s, whereas the restricted path is 278.167 m / 26 s and
Valhalla reports 0.277 km / 28.582 s. Numerical travel times differ because
the reference probe uses declared integer speed assumptions and the candidate
uses Valhalla costing. No speed calibration is inferred.

The [exploratory synthetic reference](reference-benchmark.json) and
[full Utrecht candidate](valhalla-benchmark.json) artifacts remain for
reproducibility but are **not** a head-to-head comparison. The shared-source
artifacts still do not use identical compiled graph extents. Selection is
based on the hard semantic closure contract and explicit edge identity, not
on a claim that Python is faster than Valhalla.

## Supported semantics and exclusions

Task 3.6 shall promote the selected algorithm with a **single** OSM graph
compiler and retain exact directed edge IDs, bridge-asset groups, integer
seconds/mm, reviewed profile sets, stable ties, and conservative `no`/`only`
turn treatment. Conditional, ambiguous, malformed, or unsupported OSM
restrictions must block affected access or readiness; they must never become
permissive turns. The compiler must reject or expose incomplete geometries,
unreviewed access, crossings and extent cuts. Time-dependent speeds, public
transit, dynamic Valhalla costing and automatic official road-condition
inference are outside this selected route contract. Exact vehicle-profile
mapping and Philippine source validation remain implementation gates.

This ADR does not declare municipality-scale latency, memory, model validity,
or Philippine OSM quality acceptable. Task 3.5 must pin a real source snapshot;
Task 3.6 must match reviewed graph fixtures; later load/sensitivity checks
must measure the actual study-area workload. If those checks show the selected
router cannot meet the documented limits, reopen this ADR with a candidate
that demonstrates exact run-specific closures rather than silently shipping
two production routers. Keep `pyvalhalla==3.9.1` in the dev group only to
replay this evaluation; see [dependency matrix](../dependencies.md).
